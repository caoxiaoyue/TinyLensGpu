# Opt-in cubic Hermite interpolation for pixelized sources

**Status:** ready-for-agent
**State:** claimed

## Problem Statement

Lens modelers can reconstruct a pixelized source with either a dense matrix or an operator. Both currently use bilinear source interpolation. Its spatial gradient can jump when a ray crosses a grid line. Brightness can also jump when a ray crosses the fitted bounding box and the model drops its entire interpolation row. These jumps matter when changing lens or potential parameters moves the rays during optimization.

The J0946 experiments provide a cubic Hermite source model with continuous brightness and first spatial derivatives, including at its outer support. A modeler needs to select that model through the library and use the same interpolation in either inversion backend and in potential correction. Existing fits must remain reproducible. The experiments motivate testing Hermite, while recovery on real lenses and the sensitivity of operator evidence to the interpolation and block partition still need separate validation.

## Solution

Add an explicit source interpolation choice to the ordinary pixelized source model and the standalone potential-correction renderer. Keep `bilinear` as the default everywhere that already constructs a bilinear source mapping. Enable `cubic_hermite` only through an explicit configuration, including a recorded choice when resuming a run.

Both backends use a shared calculation of each ray's neighbor indices and weights. Hermite uses the original fitted nodes and treats exterior node values as fixed zeros. Its support extends two original grid spacings beyond each side of the fitted bounding box. The library constructs weights directly for the original nodes. Maintained workflows record the interpolation and boundary convention so that reconstruction and continuation use the same source model.

## User Stories

1. As a lens modeler with an existing dense pixelized fit, I want an omitted interpolation option to select the established bilinear model, so that I can reproduce the fit.
2. As a lens modeler with an existing operator fit, I want the same bilinear default, so that an upgrade preserves my source mapping.
3. As a potential-correction user, I want a standalone renderer with no interpolation option to use bilinear, so that existing single-step and iterative runs retain their source model.
4. As a caller of the low-level matrix builder, I want its omitted-option behavior and the explicit bilinear helper preserved, so that older direct callers and image templates retain their results.
5. As a lens modeler, I want to select `cubic_hermite` on my source model, so that I can test a continuously differentiable source representation.
6. As a potential-correction user, I want to select the source interpolation on the renderer, so that I can use the same representation as the upstream source fit.
7. As a pipeline author, I want invalid interpolation names rejected at construction, so that a configuration error is visible before fitting.
8. As a lens modeler, I want the interpolation selection fixed for a constructed model, so that cached and compiled computations all represent the model I selected.
9. As a user evaluating source light directly, I want it to use the configured weights, so that its predictions agree with the inversion's source mapping.
10. As a lens modeler, I want the fitted coefficients to remain the original node intensities, so that their locations and the source prior retain their interpretation.
11. As a lens modeler with moving rays, I want continuous spatial gradients across internal grid lines in Hermite mode, so that crossing a cell edge does not introduce an interpolation kink.
12. As a lens modeler with rays just beyond the fitted bounding box, I want nearby fitted nodes to contribute in Hermite mode, so that crossing the box does not abruptly cut off the source.
13. As a lens modeler, I want the Hermite brightness and spatial gradient to reach zero at the outer support, so that rays beyond it see a dark exterior.
14. As a lens modeler, I want the fitted grid to retain exactly `n²` unknowns, so that boundary extension does not enlarge the inversion or its regularization grid.
15. As a dense-backend user, I want the shared weights assembled into the existing source columns, so that selecting Hermite requires no padded dense mapping.
16. As an operator-backend user, I want the forward and transpose to use the same weights, so that the matrix-free solve targets the same data term as the dense solve.
17. As a modeler using subpixel integration, a mask, and a PSF, I want these operations applied consistently in both modes, so that I can isolate the interpolation change.
18. As a modeler doing joint semi-linear inversion, I want the source and unit-amplitude lens-light bases to retain their coupled solve, so that changing interpolation does not discard their covariance.
19. As a user of NNLS or PNPG, I want the nodal non-negativity constraint and Hermite's signed weights documented, so that I interpret a negative interpolated value correctly.
20. As a user of the operator preconditioner, I want its native-resolution source mapping to use the selected interpolation, so that it approximates the intended curvature.
21. As a user optimizing nonlinear parameters, I want the coordinate derivatives to use the same Hermite stencil as brightness, so that I can verify their consistency with automatic differentiation.
22. As a user running a float64 comparison, I want the interpolation to retain ray coordinate precision, so that a small perturbation is represented in derivative checks.
23. As an iterative potential-correction user, I want gradients refreshed at the current corrected rays, so that the current linearization matches the chosen source interpolation.
24. As a single-step potential-correction user, I want to keep supplying my own frozen gradient callback, so that I can retain an analytic or independently supplied gradient model.
25. As a single-step Hermite user, I want the callback applied inside the extended support and zeroed at its outer edge and beyond, so that its domain follows the chosen source support.
26. As a user of a scientific calibration example, I want source and potential stencils handled at their respective widths, so that a sixteen-neighbor source works with a four-neighbor potential deflection.
27. As a user of source-incidence partitioning, I want votes based on the magnitude of each source weight, so that signed contributions to different source nodes do not cancel in the tile vote.
28. As a researcher comparing partitions, I want automatic reuse to check interpolation and partition-rule provenance, so that a matching geometry alone cannot select an inappropriate saved partition.
29. As a researcher conducting a controlled comparison, I want to supply a fixed partition explicitly and record its origin, so that I can repeat the same approximation across runs.
30. As a downstream consumer, I want saved results to record interpolation and boundary metadata while retaining the fitted bounding box, so that I can reconstruct the support and evaluate the same model.
31. As a pipeline author resuming a legacy checkpoint, I want a known pre-feature result with no mode field interpreted as bilinear, so that I can continue an old fit.
32. As a pipeline author resuming a staged fit, I want a conflicting explicit interpolation setting rejected, so that results and evidence from incompatible forward models cannot be mixed silently.
33. As a lens modeler trying Hermite on an old system, I want a fresh run to be able to reuse old node intensities as an initial source, so that I can make a controlled comparison.
34. As a J0946 researcher, I want a replay to retain its recorded hard-box, experimental zero-ring, or Hermite boundary convention, so that each saved comparison keeps its original meaning.
35. As a maintainer, I want fixed-parameter reconstruction agreement and evidence approximation error measured separately, so that I can distinguish solver accuracy from sensitivity to the partition.
36. As a researcher, I want a replay of a saved J0946 state against the experimental Hermite implementation, so that I can verify the port on actual rays and fields.
37. As a GPU user, I want preparation, preconditioner, memory, and solve costs measured for a representative source grid, so that I can judge the cost of enabling Hermite.
38. As a user considering Hermite, I want the guide and a maintained example to show explicit selection and its current validation limits, so that I can try it with an appropriate baseline.

## Implementation Decisions

1. **The source model owns the ordinary interpolation setting.** Add a validated, static `interpolation` keyword to `PixelizedSourceModel`. Add a corresponding `source_interpolation` keyword to `PotentialCorrectionRenderer`, which receives source geometry directly. Supported values are `bilinear` and `cubic_hermite`. Both defaults are `bilinear`. Dense and operator simulators read the source model's setting, including when preparing a fixed-geometry cache. Switching modes means constructing a model and its prepared state for the new mode.
2. **Keep the existing mapping seam.** Place the Hermite weight calculation beside the bilinear implementation and use a thin dispatch function with an explicit mode. Both implementations return weights, flattened original-node indices, and a geometric support mask. The established dense mapping helper accepts an optional `interpolation` keyword whose default is bilinear. Its explicit bilinear counterpart remains available with the current semantics, including for image templates. Direct source brightness evaluation and both dense mapping entry points use this same mapping definition. The dense backend assembles the existing `N_ray` by `n²` source block and the operator uses the weight-index arrays for forward gather and transpose accumulation.
3. **Use the experiment's cardinal cubic basis.** Hermite is the tensor product of centered-difference cubic Hermite interpolation in the two axes, equivalent to Catmull–Rom or Keys with parameter −0.5. It interpolates the original node intensities and uses up to sixteen neighbors per ray. Keep the original axes, spacing, fitted bounding box, and `n²` source coefficients. Exterior node values are fixed to zero by masking each exterior neighbor's contribution. Rays beyond the fitted box can still receive weights from fitted neighbors. The support ends two spacings beyond each side of the fitted box with zero brightness and first derivatives at the final edges. Generate weights directly against the original source indices without constructing a padded source array or matrix.
4. **Use the same geometric stencil for derivatives.** Compute analytic spatial derivatives from the same cell, weights, and exterior-node convention as brightness. Maintain the existing four-neighbor, hard-box, endpoint, and derivative behavior in bilinear mode. In Hermite mode a zero brightness-weight row at a virtual grid line can still have a nonzero normal derivative. The support mask describes geometry and is independent of whether a particular row has nonzero weights. Keep method and stencil width static for JIT, preserve coordinate precision, and retain the existing subpixel integration, PSF, and mask ordering.
5. **Keep the current inversion targets and approximations.** For fixed rays the forward image is linear in the original source coefficients. Retain signed Hermite weights and brightness. NNLS and PNPG constrain node coefficients. The existing regularization and adaptive templates act on the original fitted grid. The ordinary operator's native-resolution data blocks use the configured weight function while retaining their existing approximation to the subpixel and PSF data curvature. Keep the exact coupled operator actions and existing determinant approximations. Preserve the block-Schur preconditioner and unit-amplitude lens-light basis contract for joint semi-linear inversion.
6. **Respect the separate potential-correction gradient contracts.** The renderer uses the shared source stencil for brightness, adjoints, and spatial derivatives. Iterative correction recomputes the selected interpolant's gradient for the current source and corrected rays, and records the actual gradient policy. Single-step correction retains its explicit `source_gradient` input, evaluates it at the macro rays, and freezes it as before. For Hermite it uses callback values strictly inside the extended support and zeros them at the outer edge and beyond. Bilinear retains the original callback mask. Keep the single-step and iterative solve and evidence methods distinct.
7. **Partition sources and potentials using independently sized stencils.** Scientific example calibration and partition helpers validate source weight and index arrays against each other and against the common ray count. The potential deflection stencil retains its own width. Sum the absolute values of individual source neighbor weights when voting for a source tile. The forward and transpose continue to use the original signed weights. Include the interpolation and vote rule in automatic partition provenance and reuse checks along with the existing geometry. Reuse documented legacy bilinear partitions under matching bilinear conditions. Regenerate unmatched automatic partitions. Accept explicit valid fixed partitions for controlled comparisons and record their origin.
8. **Persist the choice at the workflow seam.** Record the actual `source_interpolation` and `source_boundary` in new source packages and potential-correction configuration or result metadata. Record the interpolation in resumable stage configuration even before a source package exists. Keep `source_bbox` as the fitted-node bounds and derive the support from those bounds, grid size, and boundary convention. Preserve the existing compiled inversion-result structure. Carry the setting through maintained example exporters, stage recovery, and active J0946 handoff consumers. Known old library runs without a mode field resolve to bilinear. A recorded Hermite mode carries forward as an existing explicit choice. Experimental zero-ring bilinear keeps its own provenance.
9. **Resume one forward model consistently.** Check explicit interpolation settings against checkpoint provenance before consuming saved stage state. Report a conflict and require a fresh run to change the interpolation. A fresh run may explicitly use an older source as initialization. Keep the provenance of original results and partitions when replaying archived studies. Provide an explicit Hermite example and explain how to request either mode in the guide.

## Testing Decisions

1. **Prefer existing observable seams.** Exercise public source brightness, simulator and inversion results, and the potential-correction renderer and solve entry points. Use a focused mapping check for node, stencil, and derivative cases that are difficult to isolate after imaging. Use existing workflow entry points for configuration, export, and resume tests. Compare predictions, gradients, residuals, configurations, and reported solve status through those interfaces.
2. **Establish bilinear compatibility.** Compare omitted settings and explicit bilinear through ordinary models, the standalone renderer, and the low-level dense mapping helper. Retain independent legacy bilinear regressions, including hard-box clipping, upper-edge semantics, masked imaging, and the historical single-step and iterative controls. Verify documented old artifacts can still be consumed under the bilinear configuration.
3. **Check Hermite against an independent interpolant.** On a small grid use an explicit zero-extended reference to verify nodal reproduction, signed weights, contributions to rays outside the fitted box, and zero brightness and derivative at and beyond the outer support. Include the smallest supported source grid. Check the two-sided limits across internal knots, the fitted-box edges, the first virtual lines, and the final support. A first virtual line with zero brightness and a nonzero normal derivative should exercise the distinction between brightness weights and geometric support. Check analytic derivatives against JAX automatic differentiation and finite differences at an appropriate precision.
4. **Check imaging and inversion parity at fixed conditions.** Compare direct light, dense and operator forward images, and the forward/adjoint inner product using the same interpolation, geometry, regularization strengths, mask, asymmetric PSF, and subpixel sampling. Verify fixed and freshly prepared model paths. Compare Cholesky with PCG, and NNLS with PNPG, on small problems where both converge. Check node values, model images, objective values, solver status, and the applicable full residual or KKT conditions under documented tolerances. Include a coupled source and lens-light case and preserve the supported differentiation regressions.
5. **Check both potential-correction methods.** Extend zero-potential rendering parity with ordinary pixelized imaging to both modes. Exercise the single-step callback mask inside the fitted box, within the added support, at the outer edge, and beyond it. Check the current iterative Jacobian against the forward model, its transpose identity, and small dense/operator fixed-strength reconstructions. Use the same initialization and report true residuals, the objective, and reconstructed fields on their valid domains. Existing zero-potential parity, fixed-strength dense/operator comparisons, and independent Jacobian tests provide prior art.
6. **Measure determinant approximation separately.** Use a small problem with an available dense reference and multiple block configurations. Check the operator determinant against the applicable independently assembled block approximation and measure its evidence difference from the dense calculation for the same interpolation and strengths. Report this separately from MAP differences and solve failures. Existing block-Schur log determinant checks and potential-correction principal-block evidence tests provide prior art.
7. **Exercise persistence and partition selection.** Check a fresh default run, an explicit Hermite run, and round trips of their source and correction metadata. Resume an old known bilinear checkpoint without a mode field, resume a recorded Hermite checkpoint, and reject an explicit conflict before reusing completed stages. Exercise sixteen source neighbors with four potential neighbors. Verify signed tile votes, reuse of a matching automatic partition, regeneration on a provenance mismatch, and recorded explicit fixed-partition reuse.
8. **Replay an archived J0946 state.** Use the fixed J0946 handoff and a saved cubic reconstruction, preserving its source values, potential coefficients, source grid, corrected rays, precision, and imaging settings. Run the experimental and library Hermite evaluations on the same inputs and compare ray brightness, spatial derivatives, and the prediction after subpixel integration and PSF convolution. Record the selected archive, comparison tolerances, and differences. This is a fixed-state forward and derivative comparison.
9. **Measure representative GPU costs.** Use a `100 × 100` source grid and `nsub=4` to compare bilinear and Hermite under the same representative configuration. Verify preparation and solve complete, and record mapping preparation, preconditioner construction, peak device memory, and synchronized solve time with compilation costs distinguished from warm execution. Check that memory use respects direct original-node assembly and the operator's matrix-free contract. Use measured results to identify any blocking allocation. There is no prescribed wall-time ratio or device-memory cap.
10. **Keep verification suites separate.** Put core numerical behavior and cross-module parity in the library suite, example and checkpoint behavior in the example suite, and resource measurements in benchmarks. Run them in separate processes in the `tinylens_gpu` environment. Record commands, results, precision, tolerances, and the configuration of measured costs.

## Out of Scope

- Making Hermite the default at any source interpolation entry point.
- Refitting the archived J0946 system, rerunning its outer regularization search, or establishing a scientific recovery or detection claim from the replay.
- New interpolation families, monotonicity limiters, clipping interpolated brightness, or constraints on brightness between source nodes.
- New fitted boundary coefficients, automatic expansion of the fitted bounding box, new source meshes, or changes to source prior or adaptive-template semantics.
- New optimization algorithms, changes to the physical potential deflection grid, replacement of the operator determinant approximations, or a new single-step gradient-provider API.
- A new public support-box query or extra fields in the compiled inversion result. The boundary information is recorded in workflow metadata.
- Rewriting archived experimental outputs or interpreting the experimental zero-ring bilinear comparison as the library's hard-box bilinear baseline.
